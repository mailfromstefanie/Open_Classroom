## E-reader persistence

The e-reader now uses VRChat PlayerData for personal reading progress.

Reported behaviour:
- last-read page is stored per user;
- both physical e-readers use the same storage key/code;
- therefore the two physical readers share that user's reading progress;
- persistence is personal, not shared world state.

This is the first proven-in-project implementation pattern for VRChat PlayerData and is an important reference for future small per-user persistent settings.

A final real multiplayer check is still recommended before calling this fully accepted across multiple users.

## Final planned Classroom additions

Stef considers the Classroom functionally complete apart from two final creator/teacher customization features.

### 1. Persistent entrance text

Desired experience:
- teacher can edit the text shown near the entrance;
- teacher's chosen text should persist across future visits;
- when that teacher is the first person establishing the new Classroom instance, their stored text should become the shared text for that instance;
- everyone already present and later joiners should see the same instance text.

Preferred architecture direction:
- PlayerData = the teacher's personal saved source value;
- small synced instance state = the current shared entrance text;
- load persistence only after VRChat reports the player's persistent data restored;
- do not continuously save while typing; use an explicit Apply/Save action;
- include Reset to Default.

Exact networking/authority behaviour must be implemented conservatively and tested in real multiplayer.

### 2. Persistent synchronized movable poster

Desired experience:
- teacher can paste a direct image URL, e.g. own server or a supported image host;
- poster image can be picked up and placed anywhere;
- pickup interaction should feel like the current e-reader pickup behaviour;
- UI styling/scale control may reuse the visual language of the existing local table screens, but the working table-screen system itself should not be modified;
- only a simple uniform size slider is needed;
- poster object should be synchronized so other users see its current placement;
- teacher's poster configuration should persist for future Classroom sessions.

Preferred persistent fields:
- image URL;
- position;
- rotation;
- uniform scale.

Preferred separation:
- PlayerData stores the teacher's personal persisted poster configuration;
- synchronized runtime state represents the poster actually active in the current instance;
- VRCObjectSync / ownership or another proven small authoritative transform path may be used for shared movement, but inspect existing project reset/pickup patterns first;
- late joiners must receive the current poster state;
- do not turn the local table screens into networked/persistent screens;
- do not couple this to VideoTXL or Presentation unless evidence shows a real need.

Potential reusable references:
- e-reader: pickup feel + existing PlayerData pattern;
- table screens: UI visual language and scaling concept only;
- Marker Pro/reset system: home/reset and ownership/release behaviour;
- existing reset infrastructure: only where responsibility fits.
